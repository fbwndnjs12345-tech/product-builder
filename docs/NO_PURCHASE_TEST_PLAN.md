# No-purchase test plan for GAPD-7300-only setup

## Decision

Do not change the LG U+ GAPD-7300 configuration or firmware yet. The user has confirmed that their router UI exposes a MAC Filtering list with up to 30 entries and fields for On/Off, policy (allow/block), hardware address, weekday, and time range. This makes scheduled per-MAC restriction a plausible zero-cost manual experiment, but does not prove a supported API or QR-driven automation path.

## What can be tested today at zero cost

### A. Test the app workflow on the existing PC and phone

- Run the Node.js app locally on the PC.
- Test administrator login, QR issuance, one-time claim, duplicate claim rejection, revocation, and expiry state.
- This verifies application logic only. It does not restrict any phone's Internet access.
- For a phone to open the PC-hosted claim page, both devices must be on the same trusted home Wi-Fi and the PC firewall must permit the app port. Do not expose the admin panel to the public Internet.

### B. Verify what scheduled MAC filtering actually blocks

The user's GAPD-7300 UI shows:
- Maximum 30 MAC-filter rules.
- Per-rule On/Off.
- Policy: allow or block.
- Hardware/MAC address.
- Days of week (Sunday through Saturday).
- Start and end time selectors.

This is stronger evidence than merely seeing a MAC-filter menu, but it still does not establish whether this firmware blocks Wi-Fi association, LAN access, Internet forwarding, or all of these. Nor does it establish that a QR web app can modify the rules.

**Safe manual test, only when ready:** use a spare test phone/device, not the PC hosting the app and not the user's only device for router administration. Record that test device's Wi-Fi MAC address for the current SSID (disable randomized/private address only if necessary and only for that test SSID), add a single explicit *block* rule for a short future window, and verify whether that device loses Internet while the PC and other devices remain online. Keep the router admin session on another device if possible. Remove/disable the test rule afterward and confirm the device reconnects. Do not configure a global deny rule, an allow-list for all devices, or rules for the PC/router administration device. If there is no spare test device, do not apply a rule yet.

Do not treat a successful manual schedule test as proof of dynamic QR enforcement: a fixed schedule is different from setting a distinct expiry time for each visitor.

### C. Investigate whether the router UI can be safely automated

No documented, supported GAPD-7300 API has been verified. If the user later authorizes an integration investigation, inspect browser requests generated by adding/editing a rule without saving/applying changes where possible. Do not guess endpoints or send state-changing requests. Any potential UI endpoint must be verified against the actual firmware and tested only on a spare device. Credentials must stay local and must never be committed to GitHub.

### D. Optional no-purchase network experiment

A PC-based gateway or virtual router might be testable using existing hardware, but feasibility depends on Windows version, available network adapters, and whether the PC can provide an isolated downstream network while retaining upstream Internet. Windows Mobile Hotspot by itself does not prove that per-client forwarding can be reliably and securely controlled by this Node app. Do not treat a Windows Firewall rule prototype as production-grade enforcement without verifying forwarded traffic, IPv6, client identity, and reconnect behavior.

## Actual enforcement requirement

openNDS is designed to run on a Linux/OpenWrt gateway that is the client's default gateway and can control forwarding. A portal server alone cannot block traffic on the LG U+ router. If no compatible existing device or supported router API is available, full real enforcement cannot be achieved reliably with only the GAPD-7300 and the web application.

## Safe next action

The router supports weekday/time-based MAC rules according to the actual UI. Next determine what those rules block using a spare test device, then separately investigate whether rule creation can be safely automated. Keep the existing app in simulation mode until an actual enforcement adapter has been implemented and independently verified. Only if no compatible existing gateway or supported API is available should an OpenWrt device be considered; verify the exact hardware revision in the official OpenWrt Table of Hardware before purchase.
